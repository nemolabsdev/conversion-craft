## Rules

### Grids

1. Use a 12-column grid as the web layout default: 12 is the smallest number divisible cleanly by 2, 3, 4, and 6, so it supports halves, thirds, quarters, and sixths without fractional columns. [FRAMEWORK] — gridmakerpro
2. Tie column count to breakpoint tier rather than squeezing a fixed 12 columns down to mobile: Material's spec uses 4 columns at 360dp (mobile), 8 columns at 600dp (tablet), 12 columns at desktop, with margins stepping 16dp → 24dp at those same breakpoints. [LAW] — Material Design (m2.material.io)
3. Default desktop gutter is 24px inside a 1200–1440px container, dropping to 16px on smaller viewports and rising to 32px only on very wide canvases; gutters must stay multiples of 8 to remain locked to the 8pt spacing grid. [LAW] — gridmakerpro, cross-verified against Material's 24dp tablet gutter default
4. Build sections from column spans that sum to 12 (sidebar+main as 3+9 or 4+8; three-card rows as 4+4+4; four-card rows as 3+3+3+3) so every section shares column boundaries with every other section on the page, not just internally. [FRAMEWORK] — gridmakerpro
5. Enforce cross-section alignment: a testimonial band, a pricing table, and a footer with completely different content must still share the hero's left/right gutter edges and column boundaries — a grid's authority comes from consistency across the whole page, not consistency within one module. [LAW] — Müller-Brockmann, *Grid Systems in Graphic Design* (via ben-morris.com synthesis)
6. Do not let the grid make every layout decision: Refactoring UI's explicit warning is that "outsourcing all of your layout decisions to a grid can do more harm than good" — treat it as an alignment/rhythm tool, not a substitute for compositional judgment. [FRAMEWORK] — Refactoring UI (Wathan & Schoger)
7. Break the grid only for elements that must announce themselves as exceptional — a pull-quote crossing a column line, a hero image bleeding full-width past the container, a headline jumping two type-scale steps — and keep breaks rare enough to register as deliberate, not as if alignment failed. This "broken-grid" pattern is a documented, rising 2024–2026 aesthetic (Apple, Spotify, Gucci cited as adopters) sitting alongside the bento-grid and brutalist counter-trends already logged in this curriculum's layout-spacing research. [TREND-2026] — gridmakerpro; HubSpot "Broken Grid Layouts"; Secret Stache
8. When breaking the grid for an overlap or full-bleed effect, keep at least one axis (a shared baseline, one shared margin, or a shared column start) locked to the underlying grid — escaping every axis simultaneously reads as broken rather than intentional. [FRAMEWORK] — synthesis of Secret Stache and HubSpot broken-grid case studies

### Gestalt beyond proximity

9. Figure-ground: give any element that must read as "the figure" (modal, tooltip, hero focal point) a genuine contrast break from its ground — value/color contrast, shadow, or blur on the background — because z-index/stacking order alone does not trigger the automatic foreground/background split. [LAW] — NN/g, Figure/Ground
10. Measure text-over-photo contrast at the single worst-case pixel neighborhood the text overlaps — the lightest region under the text if the text is dark, the darkest region if the text is light — never against the image's average color, since contrast can swing sharply within a few pixels. [LAW] — WCAG SC 1.4.3 methodology, applied per NN/g "Ensure High Contrast for Text Over Images"
11. Text over a photographic background must still clear WCAG SC 1.4.3 at that worst-case point: ≥4.5:1 for body/UI text, ≥3:1 for large text (≥18pt regular ≈18.5px, or ≥14pt bold ≈24px) — the same threshold used for solid backgrounds, just measured against the single hardest pixel region instead of a flat color. [LAW] — W3C WCAG 2.1 Understanding SC 1.4.3
12. Scrim opacity starting ranges: a dark scrim over a light/busy photo sits at 20–40% black; a light scrim over a dark photo sits at 40–60% white; tune within that band per image, then re-verify contrast at the lightest point under the actual text block (rule 10) before shipping. [LAW] — Google Material Design, m1.material.io/style/imagery.html (primary source, verified)
13. Prefer a gradient scrim over a flat full-image overlay whenever only part of the photo needs text protection: run it from roughly 85% opaque at the text edge down to fully transparent at the far edge, using multiple gradient stops ("eased gradient") instead of one linear stop to avoid a visible hard edge. [FRAMEWORK] — Ahmad Shadeed (ishadeed.com); Smashing Magazine Part 2
14. Validate any scrim/overlay treatment by swapping in a solid white rectangle behind the same text block and confirming it stays legible — if the technique only "works" against one specific photo and fails this generic test, the contrast margin is too thin for real photo variation. [FRAMEWORK] — ishadeed.com, corroborated by NN/g's "worst-case background image" warning
15. When a photo can't be reliably darkened without damaging the image, move the headline off the photo entirely into a flat-color panel beside or below it ("frame the image") rather than forcing a marginal overlay — this preserves real, zoomable, screen-reader-legible text instead of trading it away for a baked-in image of text. [LAW] — Smashing Magazine Part 2 (WCAG 1.4.5, Images of Text)
16. Similarity: every interactive element performing the same role (all primary CTAs, all card headers, all nav items) must share identical shape, color, and size treatment across the page — a CTA styled differently from its siblings reads as a different *kind* of action, not an emphasized one. [LAW] — NN/g Similarity, via UX Tigers synthesis
17. Common region: add a bounding container (card border, background panel) only when whitespace alone fails to group unlike-shaped elements, or usability testing shows users missing a grouping — reserve borders/fills for genuine ambiguity, since decorative boxes and full-width panels used "just in case" create clutter and measurably discourage scroll continuation ("false floors"). [LAW] — NN/g, "The Principle of Common Region"
18. Closure: an icon or logomark can omit a meaningful share of its strokes (open shapes, implied lines, disconnected segments) and still read instantly if the remaining strokes preserve the silhouette's key vertices — the three-line hamburger icon is the canonical proof. Use deliberate partial shapes for iconography; don't mistake vague icons users must guess at for "elegant closure." [FRAMEWORK] — UX Tigers Gestalt synthesis, NN/g Closure video
19. Continuity: arrange sequential content (numbered steps, a stat sequence, a timeline) along one visual line or curve, and let that same line terminate at the next CTA — the eye keeps traveling along an established line rather than jumping, so ending the line at the CTA raises the odds it gets seen next. [LAW] — NN/g Continuation, via UX Tigers

### Optical vs. mathematical alignment

20. Round or pointed glyphs (circles, triangles, diamonds) must overshoot the bounding box of straight-edged neighbors by roughly 1–5% of the shared dimension to read as equal size — human perception sees circles/points as smaller than same-size squares. Typographic precedent: ~1–3% overshoot for round capitals (O), ~3–5% for pointed capitals (A). [LAW] — Overshoot (typography), citing Peter Karow's *Digital Formats for Typefaces*
21. A play-triangle inside a circular button is not correctly centered by bounding-box math: its visual mass sits left-of-center, so a mathematically centered triangle reads as shifted left. Nudge it right by roughly 5–10% of the icon's width (commonly ~2px on a small icon) until it optically balances, and verify by rotation/inversion rather than trusting the coordinates. [FRAMEWORK] — ringcentral-ux (ss Medium); note the competing method in Open Questions
22. Apple's own icon guidance treats geometric centering as a starting point, not the destination: asymmetric icon shapes get their padding manually adjusted until they read as optically centered inside their keyline/grid shapes, verified by eye rather than by measurement alone. [LAW] — Apple Human Interface Guidelines, Foundations > Icons
23. Expect a residual optical offset whenever `align-items: center` (or any bounding-box centering API) places an icon next to text, since that API centers boxes, not visual mass: nudge pointed/triangular icons ~1px up and heavy/filled icons ~1px down from the mathematical center; purely circular icons typically need no correction. [FRAMEWORK] — baraa.app (single-source practitioner heuristic; corroborate against your own icon set before hard-coding as a token)
24. Nested border-radius does not scale linearly with padding: if an outer container has radius R and P px of padding before an inner rounded element, the inner radius should be R − P, not also R — matching outer and inner radius values produces a visibly tighter, more-squared inner corner. [FRAMEWORK] — baraa.app
25. Split icon+label padding inside a button asymmetrically, not evenly: an icon's visual density reads heavier than equal-width text, so give the icon side less padding and the text side more (e.g., ~16px icon-side vs. ~24px text-side rather than a symmetric 20/20) so the pair feels centered as a unit. [FRAMEWORK] — baraa.app
26. Run a "squint test" (blur your eyes, or blur the screenshot) on any composition before shipping — squinting erases fine detail and leaves only raw visual mass, exposing optical-weight imbalances that pixel-perfect measurement misses. [FRAMEWORK] — baraa.app, consistent with Smashing Magazine's judge-by-eye framing for balance

### Visual balance and weight distribution

27. Visual weight compounds from five factors, not size alone: size, color/value contrast, texture/density, isolation (a lone element gains weight simply by standing apart), and distance from the composition's center — an element placed near the edge needs less mass than the same element placed near the center to exert the same pull, exactly like a lever. [LAW] — Smashing Magazine, "Design Principles: Compositional Balance"
28. Choose symmetrical vs. asymmetrical balance deliberately per section rather than defaulting to centered-everything: symmetrical balance (mirrored weight on a central axis) reads formal/stable/static, asymmetrical balance (unequal-but-compensated weight) reads dynamic/energetic and is the default for modern hero sections. [LAW] — Smashing Magazine
29. Judge whether an asymmetric composition is balanced or merely lopsided by eye, not by formula: it reads as intentional when removing or resizing any single element visibly tips the whole composition, and as accidental/broken when elements could be nudged freely with no perceptible change. [LAW] — Smashing Magazine (explicit: "you use your eye... not formulas")
30. For a two-column hero (copy vs. product visual), a 60/40 split toward the copy side is the practical, buildable approximation of the golden ratio (61.8/38.2) and the most common SaaS hero pattern: the dominant 60% carries headline + subhead + CTA, the 40% carries one supporting visual that doesn't compete for the first read. [FRAMEWORK] — Elegant Themes (Divi golden-ratio hero), cross-referenced against Orizon Design's hero-pattern catalog
31. To judge whether any dominant/secondary hero split (near 60/40 through 70/30) is actually balanced, don't stop at the area ratio: the smaller side must carry enough visual weight (saturation, size, contrast, or isolation per rule 27) to act as a genuine counterweight — a 70/30 split where the 30% is a pale, low-contrast thumbnail reads as unbalanced despite a textbook-correct area ratio, while a saturated, isolated product shot at 30% area can outweigh 70% of quiet copy. [FRAMEWORK] — synthesis of Smashing Magazine's weight-factor list (rule 27) applied to hero-ratio conventions (rule 30); no single source validates a fixed 70/30 target — see Open Questions
32. Whenever a hero photo carries overlaid text, place its subject on a rule-of-thirds vertical line (left or right third), not centered — this frees the opposite two-thirds as negative space for the headline/CTA, rather than forcing text on top of the subject itself. [FRAMEWORK] — Shorthand, "The Rule of Thirds in Photography"

## Anti-patterns

- **Averaging instead of worst-casing contrast**: sampling a photo's "average" color to compute text contrast, instead of the single lightest/darkest neighborhood the text actually overlaps — a technique that can pass a contrast checker in the design file and fail the moment a real, non-uniform photo is dropped in. Violates rule 10/11.
- **One fixed scrim opacity for every hero image**: hard-coding a single overlay percentage across a whole site's rotating hero photography. Some images are already dark and get crushed; some are busy and light and the fixed value doesn't clear contrast. Scrims need per-image tuning inside the documented range (rule 12), not a single global constant.
- **Leaving pointed/asymmetric icons at their mathematical center and calling it done**: play triangles, arrows, checkmarks, and logomarks that visibly lean because no optical pass was ever run (rules 20–23).
- **Zero grid breaks, ever**: a page so grid-devout that nothing escapes the column edges, producing a result indistinguishable from a wireframe. Refactoring UI's own caution (rule 6) is that total grid obedience is itself a failure mode, not just grid violation.
- **Over-bordering ("false floors")**: wrapping every card, stat, and paragraph in its own bordered box "just in case" — NN/g explicitly documents this as clutter that discourages users from scrolling further, the opposite of the common-region principle's intent (rule 17).
- **Baking a headline into a raster image to dodge a contrast problem**: solves the visual issue but breaks zoom, breaks screen readers, and violates WCAG 1.4.5 — the correct fix is a scrim plus real text, or moving text off the photo entirely (rule 15).
- **Treating symmetric 50/50 as automatically "safe"**: a perfectly mirrored hero split isn't inherently balanced or unbalanced — it's a choice with its own connotation (formal, static) that needs to be deliberate, not a hedge against getting balance "wrong" (rule 28).
- **Escaping every axis on a "broken grid" hero**: copying an award-site asymmetric layout wholesale, with no shared margin, baseline, or column start left anywhere on the page — this reads as sloppy rather than as the intentional break it's imitating (rule 8).
- **Judging a 70/30 (or any) hero split purely by area percentage**: measuring only the pixel-width ratio and ignoring that the smaller side needs enough color/contrast/isolation weight to actually counterbalance the larger side (rule 31) — a common miss when a design is built to a ratio spec without a squint-test pass.

## Open questions

- **The play-button optical-center debate is genuinely unresolved between two credible-seeming sources.** One (ringcentral-ux) argues for an eyeballed nudge (~5–10% of icon width) toward the triangle's point. The other (erqiudao) argues the "correct" fix is finding the triangle's true geometric center via a circumscribed-circle construction, framing the nudge camp as solving the wrong problem. Both produce visually similar end results in practice; this file records both methods (rule 21) rather than picking a winner. Worth a hands-on test in Figma before encoding either as a hard token.
- **baraa.app's specific pixel/percentage values (translateX ~8%, ±1px icon nudges, R − P border-radius formula, 16/24 padding split) are single-source.** They read as sound, internally consistent practitioner heuristics, but could not be cross-verified against a second independent source in this pass. Treat as a useful starting token set, not an industry-wide constant, until validated against a second design-systems source.
- **No primary source validates a specific "70/30" hero ratio.** The only rigorously sourced, buildable hero-split convention found is 60/40 (golden-ratio-derived, Elegant Themes). "70/30" appears to be an import from interior-design/photography composition writing, not a web-design-specific finding. This file treats 70/30 as one valid point on a weight-compensation continuum (rule 31) rather than a validated fixed target — flag this distinction explicitly if a downstream skill cites "70/30" as a rule.
- **Refactoring UI's exact wording could not be fetched from the book itself** (it's a paid book, not a fetchable web page); this file relies on third-party chapter summaries, which may paraphrase rather than quote Wathan/Schoger verbatim. If a downstream skill needs an exact quotable line, re-verify against the primary book text.
- **Müller-Brockmann's primary text** (*Grid Systems in Graphic Design*, 1961) is a print book, not a fetchable web source. This file used a secondary web synthesis (ben-morris.com) for his philosophy; the historical/attribution claims should be treated as accurately paraphrased secondhand, not verified against the original 1961 text.
