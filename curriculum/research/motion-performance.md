## Rules

1. Only `transform` and `opacity` can be animated on the compositor thread without triggering layout or paint on every frame; never animate `width`, `height`, `top`, `left`, `margin`, or `padding` directly — animate a `transform: scale()`/`translate()` equivalent instead. [LAW] — web.dev
2. A 60fps animation has a 16.7ms-per-frame budget; any animation touching a layout-triggering property will drop frames under real page weight well before it visibly stutters in an isolated demo — test animations on the actual page, not a blank canvas. [LAW] — web.dev (standard rendering-pipeline math)
3. Material Design 3 duration scale: "short" 50–200ms for micro-interactions (icon toggles, small state changes, hover/press feedback), "medium" 250–400ms for standard UI transitions (cards, sheets, dropdowns), "long" 450–500ms for large-surface or full-screen transitions. Do not exceed ~500ms for any single-step transition on a sales page. [LAW] — m3.material.io
4. Material Design 3 named easing curves: standard `cubic-bezier(0.2, 0, 0, 1)`; standard-decelerate `cubic-bezier(0, 0, 0, 1)` for elements entering; standard-accelerate `cubic-bezier(0.3, 0, 1, 1)` for elements exiting. Use decelerate curves for anything appearing and accelerate curves for anything disappearing. [LAW] — m3.material.io
5. Micro-interaction duration band (hover, press, toggle): 150–250ms. Below ~150ms reads as instant (good); above ~250ms starts to feel like the UI is thinking about it rather than responding. [MIXED] — emilkowalski/skills
6. Standard transition duration band (modal open, panel slide, content reveal): 200–350ms. Complex multi-step/orchestrated transitions (page transitions, multi-element reveals): 400–600ms as a hard ceiling — never longer on a conversion-critical page. [MIXED] — emilkowalski/skills
7. Exit animations should run faster than entrance animations for the same element (e.g., enter at 300ms, exit at 200ms) — a user dismissing something is already moving to their next action and shouldn't wait for a graceful goodbye. [MIXED] — emilkowalski/skills
8. Stagger delays between list/grid items: 30–60ms per item. 100ms+ per-item stagger reads as a slideshow rather than a single reveal and measurably slows perceived load; cap total stagger time (e.g., 6 items × 50ms = 300ms max). [MIXED] — emilkowalski/skills
9. Easing-by-context rule (converged across Material Design 3, Emil Kowalski, and Smashing Magazine): ease-out for elements entering/appearing, ease-in for elements exiting/disappearing, ease-in-out for on-screen state changes/morphs, plain `ease` for hover-state transitions, `linear` reserved for continuous/looping motion only (marquees, spinners, progress bars). [MIXED] — m3.material.io, emilkowal.ski, Smashing Magazine
10. At an identical duration, ease-out reads as faster/more responsive than ease-in, because deceleration happens while the user is still watching the motion begin — this is the perceptual reason entrance animations default to ease-out rather than ease-in or linear. [LAW] — Smashing Magazine
11. Hover-triggered visual feedback (color, elevation, underline) must appear within 0.1s (100ms) of pointer-enter to register as instantaneous. [LAW] — NN/g, Response Times
12. Before revealing hover-triggered hidden content (tooltip, dropdown, flyout), require 0.3–0.5s of continuous pointer dwell on the target before triggering the reveal — this filters accidental cursor pass-through from deliberate intent. Once the dwell threshold is met, start the reveal animation within 0.1s. [LAW] — NN/g, Timing Guidelines for Exposing Hidden Content
13. When hiding hover-revealed content on mouseout, delay the hide by more than 0.5s rather than hiding instantly — this tolerates the diagonal mouse path users take moving from a trigger toward the revealed content (the "menu keeps closing on me" failure mode). [LAW] — NN/g, Timing Guidelines for Exposing Hidden Content
14. Click/tap and press feedback must be effectively immediate (within 0.1s) — an explicit click is unambiguous intent and needs no dwell confirmation. On touch devices, show the pressed-state change during the ~100–130ms finger-down-to-up window, not only after release. [LAW] — NN/g, Timing Guidelines for Exposing Hidden Content
15. Nielsen's three response-time thresholds govern all interaction timing: 0.1s (100ms) feels instantaneous, 1s (1000ms) keeps flow of thought uninterrupted (no loading indicator required below this), 10s (10,000ms) is the outer limit before attention disengages and a determinate progress indicator becomes mandatory. [LAW] — NN/g, Response Times: The 3 Important Limits
16. `prefers-reduced-motion: reduce` has been Baseline (universally supported) since January 2020 across all modern browsers — implement it; there is no browser-support excuse to skip it. [LAW] — MDN
17. For `prefers-reduced-motion: reduce` users, replace scale/rotate/parallax/large-translate animations with opacity fades or color-based transitions rather than deleting motion entirely — full removal isn't required, vestibular-safe motion (no large-object movement or panning) is. [LAW] — MDN
18. Prefer CSS scroll-driven animations (`animation-timeline: scroll()` / `view()`) over JavaScript `scroll`-event listeners wherever browser support allows (with a `@supports` fallback): they run off the main thread, GPU-composited, and are unaffected by JS jank. Tokopedia's production migration cut CPU usage during scroll from 50% to 2% and removed ~80% of the scroll-animation code. [TREND-2026] — developer.chrome.com/blog/scroll-animation-performance-case-study, developer.chrome.com/blog/css-ui-ecommerce-sda
19. Core Web Vitals "good" thresholds, measured at the 75th percentile of real user sessions: LCP under 2.5s, CLS under 0.1, INP under 200ms — all three must pass simultaneously to count as a "good" page. [LAW] — web.dev, addyosmani.com
20. INP (Interaction to Next Paint) replaced FID (First Input Delay) as the official Core Web Vital responsiveness metric in March 2024; any source or tooling still reporting FID (<100ms) thresholds is measuring a retired metric — budget and monitor against INP's <200ms threshold instead. [LAW] — Google Core Web Vitals program (cross-referenced via addyosmani.com)
21. Pages passing all three Core Web Vitals thresholds show 24% lower session-abandonment during page load than pages that don't. Treat as directionally credible (published by Google's own DevRel) but flag that the underlying primary study/methodology isn't documented in the source article itself. [MIXED] — addyosmani.com/blog/core-web-vitals
22. Documented CWV-to-business-metric case studies to cite with confidence: Vodafone Italy improved LCP 31% → +8% sales; Renault improved LCP across 10M visits → bounce rate –14 points, conversions +13%; Rakuten 24's faster page variant (performance the only difference tested) → +53.37% revenue per visitor; Meesho cut LCP from 6.9s to 2.5s → –17% bounce, +3% conversion. [LAW] — web.dev/case-studies/vitals-business-impact
23. The Google/Deloitte "Milliseconds Make Millions" study (37 brand sites, 30M+ mobile sessions) found a 0.1-second mobile load-time improvement produced measurable funnel gains: retail conversions +8.4% and average order value +9.2%; travel conversions +10.1%. Cite this specific study as the primary-research anchor for "every 100ms counts" claims rather than vaguer secondary paraphrases. [LAW] — web.dev/case-studies/milliseconds-make-millions
24. Serve images as AVIF with WebP fallback via `<picture>`: AVIF runs roughly 50% smaller than equivalent-quality JPEG and 20–30% smaller than WebP; WebP alone runs 25–35% smaller than JPEG. [LAW] — Cloudinary, cross-verified against independent 2025–2026 format comparisons
25. A combined image pipeline (modern format + responsive `srcset`/`sizes` + correct lazy-load boundary) reduces total image payload by 60–75% and improves mobile LCP by 1–2 seconds versus an unoptimized JPEG-only pipeline. [TREND-2026] — Cloudinary
26. Never apply `loading="lazy"` to the LCP image or any image likely to be in the initial viewport — this delays the exact resource Core Web Vitals measures. Use default (eager) loading for above-the-fold images and add `fetchpriority="high"` to the specific LCP-candidate image so it jumps ahead of the browser's normal layout-driven fetch order. [LAW] — web.dev
27. Apply `loading="lazy"` only to images below the fold / outside the initial viewport — native lazy-loading needs no JavaScript and is supported in all modern browsers. [LAW] — web.dev
28. Set explicit `width` and `height` attributes (or CSS `aspect-ratio`) on every `<img>`, `<video>`, and embedded-media element, including inside responsive `srcset` sets — without them the browser allocates zero height before load, and the image "popping in" pushes down everything below it, directly inflating CLS. This applies even to correctly lazy-loaded below-fold images. [LAW] — web.dev
29. Use `font-display: optional` for body-text webfonts: the browser only swaps in the webfont if it arrives within roughly 100ms of first paint; if it's later, the page keeps the fallback system font for that navigation instead of causing a layout-shifting late swap. Reserve `font-display: swap` for cases where the brand font is critical enough to justify guaranteed-but-delayed FOUT. [LAW] — web.dev, Nitropack
30. Pair `<link rel="preload" as="font" crossorigin>` for the critical above-fold webfont file with `font-display: optional` — this combination is the documented way to eliminate font-loading layout jank almost entirely, since the preload frequently wins the download race inside the 100ms window. [LAW] — web.dev/articles/preload-optional-fonts
31. Subset webfonts to only the glyphs/Unicode ranges actually used and serve WOFF2 exclusively — no WOFF/TTF fallback is needed for any current Baseline browser — to minimize critical font-loading payload. [TREND-2026] — Nitropack
32. Typical third-party script weighs 50–500KB, and sales pages commonly load 5–15 of them (analytics, chat widgets, ad pixels, session replay, A/B testing) whose combined weight frequently exceeds the site's own application code. Audit and budget third-party scripts as a first-class performance line item during build, not an afterthought added post-launch. [TREND-2026] — johnkavanagh.co.uk
33. A live YouTube iframe embed blocks the main thread for a median ~1.6s and up to 4.5s on the slowest ~10% of mobile sites tested. Replace live embeds with a static-thumbnail, click-to-load facade pattern (e.g., lite-youtube-embed) anywhere video isn't the primary above-fold content. [TREND-2026] — johnkavanagh.co.uk
34. Systematic third-party script auditing (removing unused tags, deferring non-critical scripts, replacing heavy embeds with facades) typically cuts third-party JS payload by 40–70% with a directly measurable Core Web Vitals improvement — budget this as realistic optimization headroom, not a best-case outlier. [TREND-2026] — johnkavanagh.co.uk
35. Never override native scroll physics or direction with JavaScript ("scroll-jacking") on a sales page. NN/g usability testing found most participants became at least mildly disoriented by it, and a cited real-world relaunch saw bounce rate rise 40% with contact-form conversion cut in half after introducing scroll-jacked sections. Use scroll-triggered (not scroll-hijacked) reveal animations instead — elements fade/translate in as they naturally enter the viewport while native scroll speed and direction stay untouched. [LAW] — NN/g, Scrolljacking 101

## Trends 2024-2026

- **CSS scroll-driven animations (`animation-timeline: scroll()`/`view()`) replacing JS scroll listeners.** Chrome/Edge have full support; Safari and Firefox support is landing progressively through 2025–2026. Production case studies (Tokopedia, redBus, Policybazaar) already show large CPU and code-size wins. **Shelf life: durable** — this is a platform capability shift, not a stylistic fad; expect it to become the default technique for scroll-triggered reveals once cross-browser support solidifies, ship with a `@supports` fallback until then.
- **INP as the dominant responsiveness metric, post-FID.** Replaced FID in March 2024. **Shelf life: durable** until Google's next Core Web Vitals revision — no announced successor as of this research pass, but the metric itself has changed twice already (FID→INP), so re-verify before treating any threshold as permanent.
- **AVIF as primary image format with WebP fallback.** AVIF's ~50% JPEG / ~20-30% WebP compression edge plus growing browser support makes it the current best-practice default. **Shelf life: 3–5 years** — until JPEG XL or a successor format reaches equivalent encode-tooling and browser-support maturity.
- **Third-party script facade patterns (click-to-load embeds for video/chat/maps).** Growing in adoption as third-party script proliferation on marketing sites keeps increasing. **Shelf life: durable** — addresses a structural problem (vendor scripts, not first-party code) that isn't going away.
- **`font-display: optional` + preload as the default font-loading doctrine**, replacing the older blanket "just use swap" advice. **Shelf life: durable** — standard technique, not a fad; the 100ms-cutoff mechanic is a stable platform behavior.
- **Restrained, sub-600ms "invisible" animation as a reaction against maximalist award-site motion.** Emil Kowalski's "the best animations are the ones you don't notice" philosophy and Material Design 3's short/medium duration bands both push toward fast, subtle, utility-first motion for product/SaaS/sales UI, in contrast to the slower, spectacle-driven motion common on Awwwards-style portfolio sites. **Shelf life: medium (2–3 years)** — tied to the broader "utility over spectacle" swing in B2B/SaaS design; could reverse if award-site aesthetics cycle back into commercial favor.

## Anti-patterns

- **Animating layout-triggering properties instead of transform/opacity.** Animating `width`, `height`, `top`, `left`, or `margin` forces the browser to recompute layout on every frame instead of compositing on the GPU — this is the single most common cause of janky "smooth" sales-page animations, especially on mid-tier mobile hardware where the target audience actually browses.
- **Scroll-jacking.** Overriding native scroll speed/direction to force a choreographed reveal sequence. NN/g testing found this disorients task-focused users; a cited relaunch saw bounce rate rise 40% and contact-form conversion drop by half. It optimizes for "experience" at the direct expense of the conversion action the page exists to drive.
- **Lazy-loading the LCP image.** Applying `loading="lazy"` to the hero/above-fold image delays the exact resource Core Web Vitals measures — a self-inflicted LCP regression that's easy to introduce by blanket-applying lazy-loading to every `<img>` tag rather than reasoning about which image is the LCP candidate.
- **Live third-party video embeds above the fold.** A raw YouTube iframe can block the main thread up to 4.5s on slower mobile devices — directly competing with INP and LCP on the same page section meant to build trust and drive action. Use a facade/click-to-load pattern instead.
- **Ignoring `prefers-reduced-motion`.** With universal browser support since January 2020 and 70+ million users reporting vestibular sensitivity to motion (per accessibility literature cited in this space), skipping this media query on a sales page is both an accessibility failure and an unforced conversion risk — motion-sensitive visitors who feel discomfort leave rather than convert.
- **Over-staggered reveal sequences.** Per-item stagger delays at or above 100ms turn what should read as one cohesive entrance into a visibly sequential slideshow, adding perceived load time to a page that is being judged on speed.
- **Using ease-in (or no easing / linear) for entrance animations.** Ease-in delays the perceptible start of motion at exactly the moment the user's attention is on the trigger, making the UI feel laggy even when the total duration is identical to an ease-out equivalent.
- **Citing pre-March-2024 FID thresholds as current Core Web Vitals guidance.** FID was retired in favor of INP; a "<100ms FID" claim in any 2024+ audit or curriculum material signals stale sourcing.
- **Heavy hero-section motion/WebGL on the exact page meant to convert fastest.** Award-circuit-style scroll-jacking, large WebGL hero animations, and experimental navigation are documented (see this project's `layout-spacing.md` research) to correlate with confusion and mobile failure — the same visual maximalism that wins design-award judging (weighted 40% Design / 20% Creativity, only 10% Content) works directly against Core Web Vitals budgets and the response-time thresholds in this file.

## Open questions

- **The 24% abandonment-reduction figure (addyosmani.com) is not traceable to a primary study within the source article.** It's presented as an established fact by a credible Google-affiliated author, but the article links out rather than citing methodology, sample size, or date range directly. Treat as directionally credible, not as a number to defend under scrutiny without further sourcing.
- **Emil Kowalski's specific millisecond duration bands (150–250 / 200–350 / 400–600ms) come from his companion GitHub skill repo (`emilkowalski/skills`), not verbatim from his primary essay or course landing page**, which discuss principles (ease-out for entrances, "animations you don't notice") more than they publish exact numbers. Treat the specific figures as a faithful practitioner distillation of his approach rather than a directly quotable primary-source number.
- **Material Design 3's "emphasized" easing curve may be understated here.** Search-derived documentation returned the same `cubic-bezier(0.2, 0, 0, 1)` value for both "standard" and "emphasized" curves, which is suspicious — M3's full spec defines emphasized easing as a more dramatic multi-point curve (documented elsewhere as a `linear()` function approximation, not a simple two-point cubic-bezier). Re-verify directly against `m3.material.io/styles/motion/easing-and-duration/tokens-specs` before shipping this as an exact spec value in a skill or template.
- **Third-party script cost statistics (johnkavanagh.co.uk) are single-source for this research pass** — the 50–500KB range, 5–15 script count, and 40–70% optimization-headroom figures weren't independently cross-verified against a second primary benchmark (e.g., HTTP Archive's own third-party report). Directionally reliable, but worth strengthening with an HTTP Archive citation if this becomes a headline claim.
- **Browser support for CSS scroll-driven animations changes quickly.** As of this research pass, Chrome/Edge have full support and Safari/Firefox support is landing progressively — any specific "X% of browsers support this" claim should be re-checked against caniuse.com at time of use rather than treated as fixed.
