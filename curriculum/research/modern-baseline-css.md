# Modern Baseline CSS & Web-Platform Toolkit (2025–2026) for Sales Pages

## Rules

1. Baseline classification is a fixed, computable timeline, not a subjective label: a feature is **"newly available"** the day it becomes interoperable across Chrome/Edge, Firefox, and Safari, and automatically becomes **"widely available"** exactly **30 months** later if support holds. Verify every date below directly against `web-features` data before a project ships — this document's dates were pulled 2026-08-11. [LAW] — web.dev/baseline
2. `<dialog>` is Baseline **widely available since 2024-09-14** (newly available 2022-03-14; Chrome 37+, Edge 79+, Firefox 98+, Safari 15.4+) — safe as the default implementation for any modal (confirmation, login gate, destructive-action confirm) with zero fallback concern. [LAW] — web-features `dialog`, MDN
3. Do not write manual JS focus-trap code for a `<dialog>` opened via `.showModal()` — the browser automatically makes background content `inert`, cycles Tab focus only within the dialog, and restores focus to the invoking element on close. A hand-rolled `role="dialog"` gets none of this for free and requires independently building all five behaviors: focus trap, click-outside dismissal, Escape handling that doesn't leak, focus restoration, and initial-focus placement. [LAW] — CSS-Tricks (Scott O'Hara / W3C APA WG)
4. Reserve the `popover` attribute for content that must **not** make the page inert (menus, comboboxes, non-blocking toasts, tooltips); use `<dialog>` whenever background interaction must be blocked. The Popover API is Baseline **newly available only, since 2025-01-27** — its original 2024 target slipped ~9 months on an iOS/iPadOS light-dismiss bug (fixed in Safari 18.3) — and is not yet Baseline widely available (projected ~2027-07-27 at the standard 30-month clock). [TREND-2026] — web.dev/blog/popover-baseline, web-features `popover`
5. Never style a popover's `::backdrop` to visually read as a modal scrim — popovers do not trap clicks the way `<dialog>` does, so a click can pass through the styled backdrop to whatever element sits underneath it, a documented click-through vulnerability. If the design calls for a click-blocking backdrop, that is a `<dialog>`, not a popover. [LAW] — remysharp.com (2026-05-08)
6. Set `closedby="any"` explicitly on any `<dialog>` that should support click-outside light-dismiss — `showModal()` defaults to `closedby="closerequest"` (Esc + programmatic close only), not `"any"`. The `closedby` attribute itself is **not yet Baseline** (Chrome 134+, Firefox 141+; no Safari support surfaced in the current dataset) — ship a JS click-outside fallback if Safari light-dismiss matters for the audience. [TREND-2026] — MDN `<dialog>`, web-features `dialog-closedby`
7. Style the modal scrim with `dialog[open]::backdrop { background: …; backdrop-filter: … }` directly on the pseudo-element rather than an absolutely positioned sibling `<div>` — this is spec-correct and avoids z-index/top-layer conflicts entirely. [LAW] — web.dev baseline-in-action-dialog-popover
8. Place `autofocus` on the specific interactive element that should receive initial focus inside a dialog or popover; never set `tabindex` on the `<dialog>` element itself — it is not an interactive element and does not receive focus. [LAW] — MDN `<dialog>`
9. Do not build customer-facing dialog/popover triggers on the `command`/`commandfor` button attributes yet — Invoker Commands reached Baseline **newly available only as of 2025-12-12** (Chrome 135+, Firefox 144+, Safari 26.2+), roughly 8 months old as of this research. Use `popovertarget`/`popovertargetaction` (stable since 2025-01-27) or `.showModal()` in the interim. [TREND-2026] — web-features `invoker-commands`
10. `:has()` just crossed from newly available (2023-12-19) to Baseline **widely available on 2026-06-19** — as of this research it is freshly safe to treat as a no-fallback-needed primitive for form validation and card-state styling, on the same footing as flexbox. [TREND-2026] — web-features `has`, MDN `:has()`
11. Scope every `:has()` selector to the narrowest realistic ancestor — never anchor to `body`, `:root`, or `*` (e.g. use `.field:has(input:invalid)`, not `body:has(input:invalid)`) — because the browser must re-evaluate `:has()` on every relevant DOM mutation, and a broad anchor forces a full-document re-check on every keystroke or interaction. [LAW] — MDN `:has()` performance notes
12. Inside a `:has()` selector, prefer constrained combinators (`:has(> .foo)`, `:has(+ .bar)`) over a bare descendant selector (`:has(.foo)`) — constrained combinators limit the engine to a direct child/sibling check instead of a full subtree or ancestor-chain traversal. [LAW] — MDN `:has()` performance notes
13. For inline field-validation styling, pair `:has()` with `:user-invalid`/`:user-valid`, not the raw `:invalid`/`:valid` pseudo-classes — e.g. `.field:has(input:user-invalid) { … }` — so error state only renders after the user has actually interacted with the field, never on initial page load before they've typed anything. [FRAMEWORK] — MDN form-validation pseudo-class pattern
14. Drive plan-card/pricing-toggle "selected" states with a hidden radio or checkbox input plus `:has()` on the card wrapper (`.plan-card:has(input:checked) { … }`) instead of a JS-toggled state class — this removes the JS dependency for pure visual selection state entirely. [FRAMEWORK] — `:has()` pricing-card pattern (production examples)
15. Apply `text-wrap: balance` only to short blocks — headlines, pull-quotes, captions — capped at **6 lines in Chromium** and **10 lines in Firefox**; beyond those counts the browser silently falls back to normal wrapping, which is also why the value is gated by line count at all (the balancing algorithm is computationally expensive per recalculation). Baseline **newly available since 2024-05-13**, not yet widely available (projected ~2026-11-13). [TREND-2026] — MDN `text-wrap`, web-features `text-wrap-balance`
16. Do not depend on `text-wrap: pretty` for orphan prevention on traffic with meaningful Firefox share — Firefox has **no implementation** as of this research (the feature does not qualify for Baseline "newly available" status at all in the current dataset). Ship it only as a harmless progressive enhancement for Chromium 117+/Safari 26+. [TREND-2026] — WebKit blog, web-features `text-wrap-pretty`
17. Chromium and WebKit disagree on `text-wrap: pretty`'s scope: **Chromium only rebalances the last 4 lines** of a paragraph, while **WebKit evaluates the entire paragraph** regardless of length — do not assume identical visual output across engines when using it on long-form body copy. [LAW] — WebKit blog (webkit.org/blog/16547)
18. Container queries (`@container`, `container-type`, `container-name`) are Baseline **widely available since 2025-08-14** (newly available 2023-02-14) — safe as the default responsive mechanism for any component (plan card, nav item, product tile) that must reflow against its own column width rather than the viewport. [LAW] — web-features `container-queries`, MDN `@container`
19. Set `container-type: inline-size` on the direct parent of any component you intend to query; add a `container-name` only when multiple nested containers could otherwise make it ambiguous which ancestor a given `@container` rule targets. [LAW] — web.dev baseline-in-action-container-queries
20. Container query units (`cqi`, `cqw`, `cqb`, `cqh`) cannot measure the element they are applied to — they always resolve against the nearest ancestor that has `container-type` set. Default to `cqi` for width-driven component sizing; reach for `cqmin`/`cqmax` only when scaling must explicitly track the tighter or looser of two axes. [LAW] — web.dev baseline-in-action-container-queries
21. When mixing `cqi` into a `clamp()` for fluid type inside a queried container — e.g. `clamp(1rem, 0.875rem + 0.5cqi, 1.25rem)` — keep the `cqi` coefficient low (≈0.5, not multiple whole units) relative to the `rem` base: a high container-unit contribution shrinks the influence of the user's root font-size preference and degrades zoom/accessibility behavior. [LAW] — web.dev baseline-in-action-container-queries
22. Set nested component-level breakpoints with `@container (inline-size > Nch)` in `ch` units rather than fixed `px`, when the goal is a component (e.g. a card that goes 1-column → 2-column → 3-column) that reflows consistently regardless of the font actually rendering — e.g. `@container (inline-size > 40ch)` for the first jump, `@container (inline-size > 50ch)` for the second. [FRAMEWORK] — web.dev baseline-in-action-container-queries (live example)
23. `light-dark()` is Baseline **newly available since 2024-05-13**, not yet widely available (projected ~2026-11-13) — safe to ship as the primary theming mechanism, but confirm this project's actual browser-support floor before dropping `@media (prefers-color-scheme)` fallbacks entirely. [TREND-2026] — web-features `light-dark`, web.dev/articles/light-dark
24. `light-dark()` only resolves correctly once `color-scheme: light dark` (or an equivalent explicit value) is declared on an ancestor, typically `:root`/`html` — omitting the `color-scheme` declaration leaves the function's behavior effectively light-only. Always declare both together, never `light-dark()` alone. [LAW] — web.dev/articles/light-dark, MDN `color-scheme`
25. `color-scheme` itself is Baseline **widely available since 2024-08-03** (newly available 2022-02-03) — safe to use unconditionally, including the companion `<meta name="color-scheme" content="light dark">` tag, which colors native browser chrome (scrollbars, form controls) before CSS has even loaded. [LAW] — web-features `color-scheme`, MDN
26. Implement a user-overridable theme toggle by scoping `color-scheme` per explicit state on a data attribute — `html[data-scheme="light"] { color-scheme: light }` / `html[data-scheme="dark"] { color-scheme: dark }` — while leaving `html { color-scheme: light dark }` as the system-preference default. This lets an explicit user click override the OS setting without duplicating a single color token. [FRAMEWORK] — web.dev baseline-in-action-color-theme
27. Utopia's fluid-space methodology interpolates every spacing token between two named viewport poles using `clamp()` — its live calculator's current defaults are a 360px viewport at an 18px base and a 1240px viewport at a 20px base, ratio 1.25, producing tokens like `--space-s: clamp(1.125rem, 1.0739rem + 0.2273vw, 1.25rem)`. Treat these poles as per-project configuration, not fixed constants — re-derive them from the live calculator rather than hardcoding this document's numbers. [FRAMEWORK] — utopia.fyi/space/calculator
28. Any `clamp()`-based fluid type or space value must (a) keep its maximum at **≥2–2.5× its minimum** and (b) include a `rem`-based term (not pure `vw`/`vi`) in the preferred-value middle argument, e.g. `clamp(1.5rem, 1rem + 2.5vw, 3rem)` — pure-`vw` clamps don't respond to browser zoom, which fails WCAG 1.4.4's requirement that text reach 200% scale without loss of content or function. [LAW] — Smashing Magazine, 2023-11 ("Addressing Accessibility Concerns With Using Fluid Type")
29. Utopia-style fluid scales and a fixed 8px spacing grid are in genuine tension: a fixed grid gives exact, auditable values at every breakpoint (easy QA, easy engineering handoff); a fluid `clamp()` scale eliminates visual "jumps" between breakpoints but computes a different pixel value at every intermediate viewport width, which is harder to spec and can drift off-grid mid-scale. Resolve this by generating fluid tokens whose two endpoint values land exactly on 8px-grid numbers, and accept that intermediate viewport widths will be off-grid by design — that's the tradeoff being made, not a bug to fix. [FRAMEWORK] — synthesis of utopia.fyi methodology against the 8px-grid convention
30. `forced-colors: active` is Baseline **widely available since 2025-03-12** (newly available 2022-09-12; Chrome 89+, Firefox 89+, Safari 16+) — build and test an explicit forced-colors branch for every custom-styled interactive component (buttons, cards, custom checkboxes/radios); do not assume the OS override alone produces an acceptable result. [LAW] — web-features `forced-colors`, MDN
31. Inside `@media (forced-colors: active)`, pair foreground and background exclusively with CSS system-color keywords — `ButtonFace`, `ButtonText`, `LinkText`, `Highlight`, `HighlightText`, `Canvas`, `CanvasText` — rather than the brand palette; these are the only colors the OS guarantees will retain the user's chosen contrast in forced-colors mode. [LAW] — modern-css.com high-contrast-support-without-broken-ui
32. `forced-color-adjust` (the property used to opt an element *out* of forced-colors overrides) is **not itself Baseline**, and the current dataset shows no confirmed Safari support at all — do not treat `forced-color-adjust: none` as a cross-browser-safe escape hatch; verify directly in Safari, and only use `none` after confirming the resulting manual contrast still passes under an actual forced-colors test. [TREND-2026] — web-features `forced-colors` (sub-feature status)
33. `@media (prefers-contrast: more)` is Baseline **widely available since 2024-11-30** (newly available 2022-05-31; Chrome 96+, Firefox 101+, Safari 14.1+) and must be handled as a **separate branch from `forced-colors: active`** — it targets a user who asked their OS/browser for more contrast but is *not* in a forced-colors mode, so folding its logic into the forced-colors block under-serves a "more contrast, still on-brand" preference with a full system-color override it didn't ask for. [LAW] — web-features `prefers-contrast`

## Anti-patterns

- **Hand-rolling `role="dialog"` + custom JS focus-trap when native `<dialog>` would do the job for free.** Every hand-rolled reimplementation has to independently get five behaviors right (focus trap, click-outside dismissal that doesn't false-positive on drag, Escape handling that doesn't leak to a parent, focus restoration, initial-focus placement) that `showModal()` provides automatically and correctly. Source: CSS-Tricks.
- **Styling a popover's `::backdrop` to look like a modal scrim.** A popover does not trap clicks — the visual implies modality the interaction doesn't deliver, producing a real click-through vulnerability onto whatever sits beneath the backdrop. If click-blocking is the intent, use `<dialog>`. Source: remysharp.com.
- **Unscoped `:has()` anchored to `body`, `:root`, or `*` for common UI state** (form validation, active plan card). Forces a full-document mutation re-check on every keystroke/interaction instead of a scoped, cheap one. Source: MDN.
- **Applying `text-wrap: balance` to long body copy** rather than short headline/caption blocks — beyond ~6 lines (Chromium) or ~10 lines (Firefox) it silently no-ops back to normal wrap, so it looks like it "isn't working" when it's simply out of its supported range.
- **Treating `text-wrap: pretty` as a cross-browser orphan-prevention fix.** Firefox implements none of it — any layout depending on it for correctness (rather than as a harmless enhancement) breaks for the entire Firefox user base.
- **Pure-`vw`/`cqi` `clamp()` type or space scales with no `rem` term.** Silently fails WCAG 1.4.4's 200%-zoom requirement because viewport- and container-relative units don't respond to browser zoom the way `rem` does.
- **Assuming `forced-color-adjust: none` is a safe cross-browser override.** It isn't Baseline and the dataset shows no confirmed Safari support — don't ship it as the only accessibility mitigation without direct Safari verification.
- **Folding `prefers-contrast: more` logic into the same `forced-colors: active` block.** These represent different user states (full OS-forced palette vs. a request for more contrast while keeping brand color) and conflating them under-serves the second group.
- **Shipping `closedby="any"` as the *only* dismiss mechanism when Safari matters.** The attribute isn't Baseline and has no confirmed Safari implementation in the current dataset — those users silently fall back to `closerequest`-only behavior unless a JS click-outside fallback is added.

## Open questions

- **Utopia's default viewport poles are a moving target.** The live calculator returned 360px/18px base → 1240px/20px base at the time of this research; older Utopia write-ups and some third-party tooling cite 320px as the minimum pole instead. Re-pull the live calculator at implementation time rather than hardcoding this document's numbers as permanent defaults.
- **`text-wrap: pretty` has no committed Firefox timeline.** Its Baseline status in the current dataset is `false` (not even on a newly-available track), and no source found during this research gives a Firefox ship date. Recheck before committing to it as anything beyond a progressive enhancement.
- **`closedby` and `command`/`commandfor` are both actively shipping and their support windows will shift.** `closedby` currently shows no Safari data at all; `command`/`commandfor` only reached Chrome/Firefox/Safari 26.2 in December 2025. Both dates in this document should be re-verified against `web-features` close to a project's actual ship date, not trusted as static.
- **How closely macOS/iOS "Increase Contrast" and Windows High Contrast Mode map onto `forced-colors: active` vs. `prefers-contrast: more` was not fully resolved by any single source in this pass.** The MDN/modern-css.com guidance describes the two media features' *intended* semantic split clearly, but this research did not find a source directly confirming Safari/macOS fires the same query for the same OS-level user action that Windows does. Test directly on macOS/iOS if that platform mix matters for a given client rather than assuming Windows-sourced guidance transfers exactly.
- **The 8px-grid-vs-fluid-scale reconciliation in Rule 29 is this document's own synthesis, not a rule stated outright by any single source.** Utopia's own materials don't discuss 8px-grid compatibility directly; the recommendation to anchor fluid-scale endpoints to on-grid values is an inference from combining the two source families, not a quoted best practice — flag it as such if repeating it in client-facing material.
